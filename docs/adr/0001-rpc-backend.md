# Pi runs as an RPC subprocess, not in-process through the SDK

The interface drives Pi as a child process (`<backend> --mode rpc`, through the app's own thin Backend client) instead of embedding it with `createAgentSession()` in the same Bun process. The main reason is isolation: heavy Pi work, such as re-parsing a large tool call's arguments on every delta (about 30 s of CPU for a 200 KB `write` on stock Pi, measured in `pi -p` with no TUI), would otherwise block the event loop that draws animations and handles clicks. A second reason is that `pi` and `pi-bolt` speak the same protocol, so the backend is a config value (`pi` in the repo default, `pi-bolt` locally). Pi-Bolt cannot host the interface itself, because OpenTUI needs `bun:ffi`, which its default JIT-off build does not support.

## Considered Options

- **SDK in-process under Bun**: full API access (`SettingsManager`, `SessionManager`, a complete `ExtensionUIContext`, including extension autocomplete providers and `getEditorText`), one process. Rejected for the event-loop sharing above, and because it rules out Pi-Bolt as the agent runtime.
- **Compile the interface into Pi-Bolt**: blocked by `bun:ffi`.

## Consequences

- The app has its own Backend client instead of Pi's exported `RpcClient`. In 1.5.0 `RpcClient` always runs `node <cliPath>`, so it can't start a compiled `pi-bolt`. It also copies the child's stderr to the parent's stderr, which garbles a full-screen interface, and it can't send `extension_ui_response`. Our client spawns `backend.command` directly, frames stdout as LF-only JSONL (a copy of Pi's unexported `jsonl.ts`), correlates responses by id, sends any record, and keeps stderr in memory. It's typed only with Pi's exported protocol types, so `@earendil-works/pi-coding-agent` stays a dev dependency, used for those types and for the test Backend.
- Only what the RPC protocol exposes is available. Pi's built-in TUI commands (`/model`, `/tree`, `/resume`, …) must be rebuilt as our own Modals, and extension UI calls that need a real terminal (`custom()`, `setFooter`, `setEditorComponent`, autocomplete providers) are no-ops.
- An Extension's Pi extension is loaded into the backend with `-e <path>`. On stock Pi, CLI paths load first and the first registration of a tool name wins, so ours overrides an installed one with the same name. **Pi-Bolt 1.1.6 has no such precedence** (verified with `scripts/pi-bolt-compat/run.ts`): when an `-e` Pi extension registers a tool that a Pi-Bolt package also registers (`ask_user_question` from the installed and compiled-in `@ssk_dev/rpiv-ask-user-question-lean`), Pi-Bolt refuses to load the package, prints `Tool "ask_user_question" conflicts with <our file>` on stderr and exits with code 1; it never answered `get_state`. A duplicate tool name is therefore a startup failure, not an override. The client already keeps stderr in memory, so ticket 05's Backend health should show that text. Workarounds (`-ne` was run; `pi-bolt remove` was not): `pi-bolt remove --pi-bolt <package>` takes the conflicting package out of Pi-Bolt for good (it also affects the regular `pi-bolt`); `-ne` in `backend.args` starts without any discovered or compiled-in Pi extension, which fixes the conflict (the probe tool then runs) but also drops every Pi extension the user relies on. No per-run switch excludes a single package that was found in `pi-bolt --help` or the docs; `--exclude-tools ask_user_question` was run and does not help: the conflict still stops startup. Chosen instead of those workarounds: an Extension's Pi extension never reuses an existing tool name. To replace a tool it registers its own name (`ask_user` for ask-user-question) and removes the old one from the active tools with `pi.setActiveTools()`, which works the same on both Backends and needs neither `-ne` nor `pi-bolt remove`. Whether that deactivation reaches a Pi-Bolt compiled-in tool is checked in ticket 13.
- Compiled-in Pi extensions that use Pi's TUI API are harmless in `--mode rpc` (same script, run against this machine's agent dir with the set `pi-bolt doctor` lists): stdout carried only protocol records, stderr stayed empty, and calls such as `setTitle`, `setStatus` and `setWidget` arrive as `extension_ui_request`s that the client may ignore. `setTitle` repeats for every spinner frame while the agent runs, so the interface should drop it cheaply. `pi-bolt --mode rpc` exits with code 0 within milliseconds of stdin closing while idle, which `Backend.stop()` relies on; closing it in the middle of a run is not covered.
- Extensions talk between their Pi extension and their Modules through the `editor` dialog of the RPC extension-UI protocol, which works on both backends. The protocol does not tell the client when Pi drops a dialog on its own, so the interface must close pending dialogs itself.
- Features that exist only in Pi-Bolt (subagent streams, extension views) are optional and turn on only when the backend accepts them.
