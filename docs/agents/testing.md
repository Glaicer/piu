# Testing

Rules for writing, changing and running this repo's tests.

- **Modified keys need the kitty protocol in tests.** Without it a terminal sends Shift+Enter as plain Enter, so `startPiu` turns on `kittyKeyboard` (the real renderer does by default); Alt arrives as `meta`. `<textarea>`'s default bindings are the reverse of a chat prompt (Enter inserts a newline, Alt+Enter submits), so the prompt routes keys in `onKeyDown` and calls `event.preventDefault()` to skip them.
- **Tests go through `startPiu`** (`test/harness.ts`), the seam spec.md already agreed, so use it without confirming a seam.
  - A test that passes on its first run isn't done until you break the code under test on purpose and watch it go red; the Restart test once passed on stale state alone. Mutate by replacing the value under test with a constant: a copy or spread of a Solid store still tracks, so that mutation stays green and proves nothing. Copy the file to the scratchpad before breaking it, because `git checkout` can't restore uncommitted work.
  - A `waitForFrame` predicate waits for everything the test asserts next, or the first matching frame can be mid-render (`isFormatted` flaked this way). Before asserting that something is absent (`not.toContain`), wait for a frame that shows the Backend data it would come from has arrived, or the check passes before the data exists. An overlay such as the autocomplete list is drawn over Panel text, so assert on a whole line (`startsWith`), not `includes`. Output that a view cannot show (scrolled out of it, behind a Modal) cannot be waited for either, so sync on a visible change sent after it, such as a card status. `panelText(frame, column, row)` in the harness returns the text of the Panel that contains that column and row, so assert on one Panel instead of the whole frame.
  - Run a new file of frame tests 10–15 times in a row before closing the ticket. A timed-out `waitForFrame` prints the whole frame, so run tests through a filter, `bun test <file> 2>&1 | grep -a "^(fail)\| pass\| fail" | cut -c1-200`, and read a full frame only for the one failing test. `-t` takes a regex, so escape parentheses in a test name. `pnpm check` takes about two minutes, so run it alone, not chained after other commands, and pass the Bash tool's own `timeout: 600000` (or `run_in_background`), because a shell `timeout` does not lift the tool's 120 s limit. `bun test` stops a test after 5 s, so a test with a deliberate wait runs with `--timeout 20000`.
  - When a spec story names several ways to do one thing (mouse or keyboard, default or given position), each way gets its own test.
- **Native frame stats can't see re-highlighting.** `getNativeStats().frameWork` misses JS and worker work. To bound streaming render cost, spy on `getTreeSitterClient().highlightOnce` (the singleton `CodeRenderable` uses by default) and bound what each call highlights. This is the agreed seam for render-cost tests.
- **Theme follows `renderer.themeMode`, and tests report a background by emitting an OSC 11 reply on `renderer.stdin`** (`startPiu({ terminalBackground })`, `reportTerminalBackground`). The reply arrives after the first render, so the Theme is a Solid store, and a Module reads `theme.accent` inside JSX or an effect, never once into a constant (the chat's `SyntaxStyle` is a memo for that reason). OpenTUI colors an unparsable color string magenta without throwing, so config validates `#rrggbb` itself.
- **Animation tests drive a `ManualClock`.** `startPiu` blanks `animations` to `false` unless the test's config says otherwise, so the regular suite never animates. A test that wants motion passes `animations: true` and `clock: new ManualClock()` (from `@opentui/core/testing`), then steps `clock.advance(20)` + `renderOnce()` and reads the frames; time never moves on its own. One big `advance` hands the whole delta to a timeline that a timer callback just created (the Toast's exit), so advance in small steps near a timer. Toast timeouts run on `renderer.clock` for the same reason. `captureCharFrame` has no colour, so the motions are slides and row reveals, never fades: assert on a text's row or column.
- **Scripted replies can be steps** (`FauxStep` in `test/harness.ts`: `thinking`, `text`, `toolCalls`, `error`). A step with tool calls needs another reply after it, because Pi calls the model again with the result. An `error` such as `529 overloaded` is retried, while `400 invalid request` is not. A compaction spends two scripted replies. Assert "running" with a slow `bash` command (`sleep 0.6`), since `read` finishes between frame polls.
- **`layout.test.ts` places the built-in `input.prompt` in a Panel of its own height.** When you change the prompt's height, or the default Layout's input sizes, update that test's Panel too. The default input Panel is sized to its content, so the prompt's fixed `height` on its textarea sets the Panel's 5 rows, and `ask-user.test.ts` asserts those rows.
- **Extension UI tests drive Pi through the `ui` tool** (`uiTool` in `FauxScript`). Its schema is a plain JSON object, because `typebox` is not a dependency here. `renderer.setTerminalTitle` throws `InvalidPhase` in the test renderer, so a test that spies on it mocks the implementation.
- **`startPiu` sets `PIU_HOME` to its temp `dir` and copies `extensions` (a fixture folder under `test/fixtures/`) into `<dir>/extensions`**, so a fixture runs from outside the repo like a user's, with no `node_modules`. `homeFromHomeDir` puts `.piu` under a temp `$HOME` with `PIU_HOME` unset instead. `piuHome()` reads `process.env.HOME` first because Bun's `homedir()` ignores a later change to it. With no config the Backend would be the real `pi`, so a test never starts the app without the harness's config.
- **A fixture Extension imports values only from `solid-js`, `@opentui/*` and itself; type imports from anywhere are fine.** `import type` (the fixtures use it for `src/module.ts`) is erased, so it resolves nowhere at run time and costs nothing. A value import of `src/` or of a test file fails in the copied folder, so a fixture reaches the test through `globalThis.piuTestHooks` (`test/hooks.ts`), and one that needs a `src/` helper carries its own copy (`stacker`).
- **Bun's module cache is shared by every test in a file that uses the same `dir`.** A fresh temp `dir` copies a fixture to a new path, so it loads again; a test that reuses `dir` (Restart) or imports a test file does share state. To assert that an Extension was or was not loaded, use a fixture that no other test places.
- **Pi lists a model for every provider with credentials in the environment**, so the author's `OPENROUTER_API_KEY` put hundreds of real models in the picker. `startPiu` blanks env vars matching `API_KEY|_TOKEN|_SECRET` for the Backend; keep any new test launcher doing the same.
- **The `/` list shows 8 rows and every app command is in it**, so a new command pushes entries out of view. Autocomplete tests type a narrowing query (`/re`) instead of a bare `/`, and a list row starts with the Panel border (`│ /name `), not with the name.
- **A new, resumed or forked Pi session re-runs the faux extension, so a test script's replies start again from the first.** Prove "fresh session" with `{messages}` or `{lastUser}`, not with reply order. Pi's RPC cannot branch inside one session, so `branchBackCommand` navigates the tree from a fixture command.
- **An automatic compaction test sets `contextWindow` in the script**, and `startPiu` writes `reserveTokens: 0`, so Pi compacts once the context passes the window. `startPiu` runs the app in its temp `dir` unless the test passes `cwd`, so the repo's `AGENTS.md` stays out of Pi's system prompt. The system prompt alone is about 1630 tokens, so a window of 1660 is crossed by the second short turn (only a band about 10 tokens wide works); re-measure it (compact with a tiny window and read `tokensBefore`) after upgrading Pi.
- **When two mechanisms deliver the same result, assert the state between them.** Click tests stayed green with the click guard removed, because the typed-key redirect still carried the text into the input; the test now checks the focus indication right after the click. Mutate each mechanism alone to see it.
- **A mutation must fail the test you aimed it at.** A mutation that does not compile fails the whole file, which proves nothing; read the first failure's message. Confirm the mutation applied (`git diff --stat`) before reading a green run as a survivor: a `sed` that matches nothing looks the same, and with the grep filter above a survivor shows only ` 1 pass`.
- **A run that must stay blocked until the test says so uses a `bash` loop on a release file**, not `sleep N` (`blocker()` in `test/pending.test.ts`): `while [ -d DIR ] && [ ! -e DIR/release ]; do sleep 0.05; done`. The `-d` test ends the loop when the folder is removed, so a failed test leaves no loop behind. A frame after the release can hide a stuck state: assert at the first frame that shows the next event, since the end of the run cleans up some state.
- **A Pi extension in a test can slow Pi down on purpose** (`test/fixtures/pi-extensions/slow-input.ts` delays every `input`, `slow-compact.ts` holds a compaction open), which is how a test gets a refusal such as "Cannot submit a prompt while compaction is in progress" at a time it chooses.
- **`test/fixtures/pi-extensions/shell-background.ts` stands in for the installed `@pify/shell-background`** (place it with `installedPiExtensions`; `backendEnv` sets `PIU_STANDIN_AUTO_MS` for the auto-background threshold and `PIU_STANDIN_DELIVER=0` to switch the end-of-turn delivery message off, which would otherwise start a turn and use up a scripted reply). It copies what the real one does that matters here: a sidecar for every job, foreground ones included, `details.background` only on a result that returns the job, delivery held to a turn boundary, and every job killed when the session ends. Check it against the real source before changing the pin. A pin that goes away is polled every 250 ms, so wait for the frame instead of asserting right after another event.
- **`test/fixtures/pi-extensions/subagents.ts` stands in for the installed `@chthub/pi-subagents`** (place it with `installedPiExtensions`; `subagentsControl()` in `test/subagents-control.ts` gives the `backendEnv` and steers it). It has no child processes: the test writes commands (`say`, `toolResult`, `status`) to a control file, and the stand-in turns them into what the real package leaves behind, a `pi-subagents-roster` entry in the parent session on every change and a child session file that appears with the first assistant message. `agent_spawn` returns at once with `run_in_background` and blocks until a non-running `status` otherwise. Check it against the real source before changing the pin. `freshSessionCommand` in the script adds `/fresh`, a session replacement the app does not start itself.
- **Quit and restart are tested on a real process** (`test/lifecycle.test.ts`, `spawnPiu` in `test/process.ts`): `bin/piu.ts` runs on a Bun pseudo-terminal, apart from the test runner, with the same temp dir, Config and faux Backend as `startPiu` (`prepareFixture` in the harness). `spawnPiu` starts it through `test/session-launcher.ts`, which calls libc's `setsid` and `TIOCSCTTY` over `bun:ffi` (Linux and macOS) and then runs `bin/piu.ts` in the same process, so the pty is its controlling terminal and a runner that dies hangs piu up; dispose sends SIGTERM, which the launcher forwards, and kills the session's group only after a grace. A SIGKILL to the launcher alone leaves the app running, and an app still waiting for its Backend installation reads nothing that would tell it the terminal is gone. The terminal output has its escape sequences stripped and is searched for text, so a reply names the prompt it answers (`{lastUser} has {messages}`), or an old line would match a new one. `PIU_PID_LOG` makes the faux extension log each Backend's pid and parent (the app) pid, which is how a test checks that a process is gone or replaced; Pi loads its extensions again on `/new`, so one Backend logs `start` more than once and `starts()` counts distinct pids. `leftModes` checks that the terminal modes the app set are off at the end. Two instances share one `prepareFixture` dir and `persistSession`, the setup where `-c` would pick the neighbour's session. `bun test` stops a test after 5 s, so these tests set their own timeout.
- **`startPiu` switches the Backend update check off** (`createApp({ updateCheck: false })`), because it would run `--version` and call pi.dev and GitHub, and the dev dependency Pi is older than the live release. A test that wants it passes `updateCheck: releaseSources({...})` (`test/releases.ts`: URL to canned `Response`, `Error` or a function, and it records the calls and abort signals) and `backendCommand: fakeInstall(...).command` (`test/backend-install.ts`: a stand-in Backend in the npm, pnpm, bun or curl layout whose `--version` reads a file and which otherwise becomes the harness's `env <pi> …` command line; `setVersion` changes what the next launch sees). Two launches that share a `dir` share the seen-versions file. A Modal may be open before its Markdown is drawn, so prove "no Modal" by typing and seeing the text reach the prompt (`settled` in `test/changelog.test.ts`), not by the absence of the notes' text.
- **`/update` tests use `updateFixture` (`test/update-install.ts`) and its `appEnv`.** Its PATH contains stand-in managers that validate the target and arguments; use them instead of running real package managers. Process tests pass that environment to `spawnPiu` and preload `test/fixtures/update-releases.ts` through `BUN_OPTIONS`, so the launcher, restarted app and worker all stay offline. They also blank `PI_OFFLINE` and `PI_SKIP_VERSION_CHECK`, which the app inherits from the runner's environment: either one drops the release notes from the changelog the tests wait for. `startPiu` without `updateCheck` makes no release requests, so `/update` there only reports that release checks are off. The installer can print an error before it exits: a retry test waits for the final `Installer failed` Toast, not merely the error's words in live progress. In process tests use kitty `ESC [27u` when typing immediately after Escape; bare Escape followed by text can be decoded as Alt plus the first character.
- **Every app in a test gets a recording clipboard** (`recordingClipboard` in `test/harness.ts`, `piu.copied` lists the writes), because the real one is the developer's own and `copyToClipboardOSC52` throws in the test renderer. Existing tests click on text, and each click starts a selection. `startPiu({ clipboardError })` makes it throw (`Error`) or report that no destination worked (`"reports"`). A single click or zero-width drag still emits a `selection` event, with empty text. Two clicks on one cell within a moment count as a double click (a word selection), so a test that clicks where it just dragged must wait or use another cell. The real host and OSC 52 writes are not covered by tests.
