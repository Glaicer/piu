# 01: Сразу показывать сообщения, ожидающие завершения блокирующего процесса

**What to build:** Отправленное через поле ввода сообщение сразу появляется в agent Panel, даже когда Backend занят блокирующим процессом. Пока сообщение ожидает обработки, у него есть заметный статус ожидания. Пользователь видит, что сообщение отправлено, и не отправляет его повторно из-за отсутствия обратной связи.

**Blocked by:** None (can start immediately).

**Status:** done

## Как воспроизвести

1. Запустить блокирующий процесс и дождаться, пока агент начнёт ждать его завершения.
2. До завершения процесса ввести сообщение и отправить его через поле ввода.
3. Проверить чат до и после завершения процесса.

По сообщению пользователя, текст исчезает из поля ввода, но появляется в чате только после завершения процесса. При подготовке тикета поведение не воспроизводилось.

В установленном Pi extension `@pify/shell-background` 0.7.0 блокировать ход агента могут выполняющийся в foreground `bash` и ожидание фонового задания через `shell_status` с положительным `wait`. Баг относится к видимости ожидающего сообщения, а не к заморозке интерфейса или к необходимости прервать процесс.

## Критерии приёмки

- [x] После отправки сообщение видно в agent Panel до завершения блокирующего процесса; ждать следующего ответа модели или начала обработки сообщения не нужно.
- [x] У ожидающего сообщения есть текстовый статус ожидания и визуальное отличие от обычного сообщения через токены темы; различие понятно не только по цвету.
- [x] При начале обработки статус ожидания снимается. В истории остаётся одно сообщение, без дубликата после получения сообщений от Backend.
- [x] Несколько отправленных во время ожидания сообщений видны по отдельности и в порядке отправки. Два сообщения с одинаковым текстом не сливаются в одно.
- [x] Сохраняется семантика отправки: Enter во время работы агента — steering, Alt+Enter — follow-up. Модель получает каждое сообщение один раз в соответствующем режиме.
- [x] Esc по-прежнему очищает очередь, прерывает текущий запуск и возвращает ожидающие сообщения в поле ввода. Их ожидающие записи исчезают из чата, и модель их не получает.
- [x] Если Backend отказывает в отправке, видна ошибка, текст не теряется, а сообщение не остаётся в чате с ложным статусом ожидания.
- [x] После перехода в другую сессию в ней не появляются ожидающие сообщения предыдущей сессии.
- [x] Регрессионные проверки через пользовательский ввод и кадры приложения подтверждают состояние до завершения управляемого медленного процесса, переход к обычному сообщению, отсутствие дублей и отмену очереди. Проверяется и получение текста моделью; тест, увидевший сообщение только после завершения процесса, не считается достаточным.

## Comments

- Сейчас поле ввода очищается при отправке, а чат показывает пользовательское сообщение только после события о нём от Backend. Отдельного отображения ожидающих исходящих сообщений нет; это наблюдение по коду, не подтверждённая воспроизведением причина бага.
- Установленная версия Pi документирует `queue_update` с полными очередями steering и follow-up. При реализации нужно сверить момент удаления из очереди с появлением сообщения в истории, а не считать отсутствие сообщения в очереди доказательством его потери.
- Тикет независим от закрепления фоновых процессов: его можно проверить с обычным медленным `bash`, без установленного shell-background. Тесты используют изолированный Backend и не обращаются к личной конфигурации Pi.
- Реализация: `PiState.pending` — упорядоченный список ожидающих сообщений с `id`, текстом и режимом (`prompt`, `steer`, `followUp`); одинаковые тексты не сливаются. Запись добавляется при отправке, а убирается в том же обновлении, что добавляет пользовательское сообщение из `message_start`; кадра с обоими нет. Совпадение идёт по точному тексту, иначе уходит самая старая запись: Pi ставит в очередь развёрнутый текст шаблона или навыка, и `/greet Ann` приходит как `Hello Ann, welcome`.
- Отклонение: `queue_update` не используется. Пока запись видна, ждать очередь Pi не нужно, а точное соответствие записи и очереди нарушает гонка между ответом на `prompt` и началом сообщения (ответ может прийти уже после `message_start`). По коду Pi (`agent-session.js`) сообщение удаляется из очереди перед выдачей `message_start`, поэтому исчезновение из очереди не считается потерей.
- Отклонение: ожидающую запись получают и обычные `prompt` в простое (`[sending]`), а не только steer и follow-up. Так отказ Backend и «медленный» Backend обрабатываются одним путём; запись исчезает при `message_start`, при `handled`, при отказе или смерти Backend.
- Исправлено попутно: текст отказанного сообщения терялся, если в поле ввода уже было другое. Теперь он добавляется перед ним через `restore`.
- Исправлено попутно: Esc сразу после отправки мог опередить сообщение, которое Pi ещё не поставил в очередь, и сообщение выполнялось после прерывания. `abort()` теперь ждёт ответов на отправки, которые ещё в пути, и только потом шлёт `clear_queue`.
- Очистка: ожидающие записи с полученным ответом снимаются на `agent_settled`; все записи — при смерти Backend, `attach` и смене сессии.
- Не воспроизводилось: «текст пропадает из поля и не появляется в чате». Тест на медленный Backend (Pi extension с `input`-обработчиком, задержка 600 мс) воспроизводит близкое состояние и был красным до исправления. Тест отказа печатает текст сразу после отправки; при любом порядке прихода отказа и набора ожидаемый результат в модели один и тот же (`refused text\n\ntyped later`), но какой из порядков случился, тест не различает.
