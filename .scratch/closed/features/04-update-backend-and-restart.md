# 04: Обновлять выбранный Backend через /update и перезапускать Pi и piu

**What to build:** Локальная команда `/update` скачивает и устанавливает обновление настроенного Pi или Pi-Bolt независимо от того, установлен он через curl-установщик, npm, pnpm или bun. После подтверждённого успешного обновления автоматически перезапускаются Backend и инициировавший инстанс piu, продолжается текущая сохранённая сессия, а в Modal показывается changelog установленной версии. Другие работающие инстансы не перезапускаются и не закрываются.

**Blocked by:** 02 — Команды полного перезапуска и выхода из piu; 03 — Проверять обновления Backend и показывать changelog при запуске.

**Status:** done

## Критерии приёмки

- [x] `/update` доступна в slash-автодополнении и обрабатывается локально, без отправки модели или добавления в очередь сообщений Backend. Одна проверка обновлений при старте не запускает установку без этой команды.
- [x] Обновляется конкретная установка настроенного Backend и только его семейство. При нескольких копиях Pi или Pi-Bolt не обновляется случайная глобальная копия, не меняется выбор Backend, не затрагиваются зависимости репозитория piu.
- [x] Поддерживаются все восемь сочетаний: stock Pi и Pi-Bolt, каждый установленный через curl, npm, pnpm или bun. Способ обновления соответствует происхождению установки, сохраняет её расположение и не переводит её молча под управление другого менеджера пакетов.
- [x] Штатные механизмы обновления и проверки целостности используются без отключения их защит. Для Pi-Bolt сохраняются вариант сборки и настройки включённых Pi extensions, которые поддерживает его штатный updater. Вывод команды с ручной инструкцией по установке не считается состоявшимся обновлением.
- [x] Во время загрузки и установки видны выбранный Backend и ход операции. Вывод установщика не пишется поверх терминального интерфейса; интерфейс остаётся отзывчивым.
- [x] Повторный `/update` не запускает второй установщик. Два инстанса, использующие одну установку, не изменяют её одновременно; ожидающий или повторный запрос получает понятный результат, а не повреждает установку.
- [x] После завершения установки проверяется фактически установленная версия целевого Backend. Только подтверждённое обновление запускает автоматический полный перезапуск Pi и piu по правилам тикета 02, без необходимости вручную вводить `/restart`.
- [x] После перезапуска видна та же сохранённая сессия и Modal с changelog действительно установленного обновления по правилам тикета 03. Активная работа старого Backend не воспроизводится автоматически.
- [x] Перезапускается только инстанс, выполнивший `/update`. Другие инстансы продолжают работу, даже если используют тот же установленный Backend; новый бинарник будет использован ими при их собственном следующем запуске.
- [x] Сетевая ошибка, отказ установщика, недостаток прав или невозможность определить происхождение установки показываются как ошибка без ложного успеха и автоматического перезапуска. Установщик не подменяется случайной командой, привилегии автоматически не повышаются; повторная попытка после устранения причины возможна.
- [x] Если новая версия не требуется, пользователь получает сообщение об актуальной версии без ненужной переустановки и changelog о несуществовавшем обновлении. Настройки, credentials, сохранённые сессии и personal Extensions не удаляются.
- [x] Проверки покрывают матрицу из двух Backend и четырёх способов установки, ошибки и повторный вызов. Процессный сценарий подтверждает автоматическую замену обоих процессов, продолжение сессии и changelog после запуска, а сценарий с двумя инстансами — сохранение работы соседнего. Установщики и установки тестовые; реальные менеджеры пакетов и личные программы пользователя не обновляются.

## Comments

- Пользователь подтвердил автоматический перезапуск Pi и piu после успешного `/update` и поддержку curl, npm, pnpm и bun. Под `npn` в сообщении принят npm.
- У stock Pi команда обновления самого Pi отличается от обновления Pi extensions и каталогов моделей. У Pi-Bolt свой updater; документация отдельно описывает установки через менеджеры пакетов, проверку подписей и восстановление набора скомпилированных Pi extensions. Нельзя свести поддержку всех способов к одному глобальному npm install или к запуску случайного бинарника с тем же именем.
- Обновление общего файла установки не означает разрешение закрыть все использующие его процессы. Перезапуск и cleanup ограничены инстансом-инициатором, как в тикете 02.
- Будущая задача: отдельно продумать механизм обновления самого piu — источник и формат релизов, определение способа установки, проверку целостности, безопасную замену, восстановление после сбоя и поведение нескольких инстансов. Этот тикет не устанавливает новые версии piu и не решает заодно его release packaging.
- From 02: автоматический перезапуск после обновления — это `actions.restart()` из `UiActions` (`src/app.tsx`, `leave`). Он завершает Backend, освобождает терминал и через лаунчер `bin/piu.ts` запускает новое приложение с `--session <текущий файл>`. Отдельный перезапуск писать не нужно. Флаги выбора сессии в `backend.args` личного Config при перезапуске не вырезаются. Тест на процессах: `spawnPiu` и `prepareFixture` (`test/process.ts`, `test/harness.ts`), пример в `test/lifecycle.test.ts`.
- From 03: Определение установки (`detectInstall`, id = семейство + realpath команды), источники релизов (`releaseSource`), хранилище версий (`createVersionStore`, файл `$PIU_HOME/backend-versions.json`) и Modal (`changelogModal`) уже есть. Способ установки (curl/npm/pnpm/bun) 03 не определяет — это для `/update`. После обновления Modal откроется сам при следующем запуске, пока предыдущая версия в файле старее установленной; если `/update` перезапускает piu, ничего дополнительно записывать не нужно. Уведомление о доступной версии уже говорит «Run /update».
- Происхождение установки определяется отдельно от версии (`src/install-origin.ts`) по managed-install marker, манифесту и проверенной bin-ссылке пакета, метаданным pnpm-группы и глобальным корням npm/Bun. Обновление идёт только через собственный менеджер найденной копии с явным размещением; npm — `--prefix`, Bun — `BUN_INSTALL_GLOBAL_DIR`/`BUN_INSTALL_BIN`, pnpm — `update -g --latest` с `global-dir`/`global-bin-dir`. При нескольких pnpm-группах с пакетом обновление отказывает, а не выбирает случайную. Зависимости репозитория piu не затрагиваются.
- Для curl-установок вызывается штатный self-updater выбранного бинарника; `PI_SELF_UPDATE_COMMAND`/`selfUpdateCommand` отказной путь, потому что эти переменные заменяют updater, а не обновляют установку. `PI_CODING_AGENT_DIR`, заданный в аргументах Backend, учитывается при чтении этого setting. У Pi-Bolt удаляются только `PIBOLT_UNVERIFIED`/`PIBOLT_ALLOW_UNSIGNED`; вариант сборки и настройки extensions остаются на его штатном updater.
- Установка и проверка версии выполняются отдельным worker-процессом; он переживает закрытие инициатора и держит межпроцессную SQLite-блокировку в общем `/tmp` для uid. Та же блокировка сериализует `--version`, первый RPC-запуск и ленивую загрузку native-сборки Pi-Bolt, поэтому второй инстанс получает понятный отказ. Проверка версии ждёт до 30 минут: первый запуск Pi-Bolt из пакета может скачивать сборку. Перезапуск — только после подтверждённой установки.
- Changelog после смены realpath: перед перезапуском история установки переносится на новый id, а в приватный файл рядом с `PIU_HANDOFF` пишется receipt со старой версией. Receipt нужен, если соседний инстанс успел отметить общую новую версию просмотренной; Modal очищает его при закрытии. Стартовая проверка обновлений ждёт первый ответ Backend, чтобы медленный RPC-старт Pi-Bolt не потерял changelog.
- Проверки: `test/update.test.ts` — матрица 2 семейства × 4 способа на временных установках, ошибки, повтор, уже актуальная версия, autocomplete/очередь, pnpm-группы, переопределённый updater; `test/update-process.test.ts` — замена обоих процессов, продолжение сессии, Modal, два инстанса и соседняя активная работа, закрытие инициатора во время установки, ленивая загрузка Pi-Bolt, медленный RPC. Полный `pnpm check`: typecheck и Biome зелёные, тесты 367/368. Падение `polish.test.ts` про автоматическую компакцию воспроизводится на чистом `HEAD` в этой среде и к тикету не относится.
- После ревью:
  - stock Pi через npm, pnpm и bun обновляется с теми же флагами, что передаёт штатный updater Pi: снят настроенный пользователем порог возраста релиза (`--min-release-age=0`, `--minimum-release-age=0`, для pnpm `--config.minimum-release-age=0`). Это осознанное отступление от «без отключения защит»: Pi сам так делает, потому что pi.dev объявляет релиз сразу после публикации. pnpm 12.3.4 молча игнорирует camelCase-ключ `--config.minimumReleaseAge`, который передаёт Pi; проверено на временном global-dir. Для Pi-Bolt флаги не добавлены, его документированные команды порог сохраняют. pnpm по-прежнему вызывается с `update -g --latest`, без фиксированной версии; worker отклоняет версию ниже целевой.
  - Запуск piu, пока установку Pi-Bolt держит другой инстанс, теперь ждёт освобождения и пишет в терминал `piu: waiting for another piu to finish with this Backend installation`, а не завершается через 2 с. Если подготовка Pi-Bolt дольше секунды, piu сообщает, что первый запуск скачивает нативную сборку. Повторная попытка из интерфейса (`restartBackend`) по-прежнему отказывает через 2 с.
  - `startPiu` без `updateCheck` больше не отправляет `/update` в настоящую сеть: команда сообщает «Release checks are switched off».
  - Падение `polish.test.ts` после слияния с `main` не повторилось: полный `pnpm check` дал 420/420.
  - Подтверждено по пакету `pi-bolt@1.2.1`: `PIBOLT_UNVERIFIED` (`install.sh`) и `PIBOLT_ALLOW_UNSIGNED` (`install.cjs`) существуют, а пакетная установка на Linux и macOS скачивает сборку при первом запуске.
