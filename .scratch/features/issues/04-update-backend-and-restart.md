# 04: Обновлять выбранный Backend через /update и перезапускать Pi и piu

**What to build:** Локальная команда `/update` скачивает и устанавливает обновление настроенного Pi или Pi-Bolt независимо от того, установлен он через curl-установщик, npm, pnpm или bun. После подтверждённого успешного обновления автоматически перезапускаются Backend и инициировавший инстанс piu, продолжается текущая сохранённая сессия, а в Modal показывается changelog установленной версии. Другие работающие инстансы не перезапускаются и не закрываются.

**Blocked by:** 02 — Команды полного перезапуска и выхода из piu; 03 — Проверять обновления Backend и показывать changelog при запуске.

**Status:** ready-for-agent

## Критерии приёмки

- [ ] `/update` доступна в slash-автодополнении и обрабатывается локально, без отправки модели или добавления в очередь сообщений Backend. Одна проверка обновлений при старте не запускает установку без этой команды.
- [ ] Обновляется конкретная установка настроенного Backend и только его семейство. При нескольких копиях Pi или Pi-Bolt не обновляется случайная глобальная копия, не меняется выбор Backend, не затрагиваются зависимости репозитория piu.
- [ ] Поддерживаются все восемь сочетаний: stock Pi и Pi-Bolt, каждый установленный через curl, npm, pnpm или bun. Способ обновления соответствует происхождению установки, сохраняет её расположение и не переводит её молча под управление другого менеджера пакетов.
- [ ] Штатные механизмы обновления и проверки целостности используются без отключения их защит. Для Pi-Bolt сохраняются вариант сборки и настройки включённых Pi extensions, которые поддерживает его штатный updater. Вывод команды с ручной инструкцией по установке не считается состоявшимся обновлением.
- [ ] Во время загрузки и установки видны выбранный Backend и ход операции. Вывод установщика не пишется поверх терминального интерфейса; интерфейс остаётся отзывчивым.
- [ ] Повторный `/update` не запускает второй установщик. Два инстанса, использующие одну установку, не изменяют её одновременно; ожидающий или повторный запрос получает понятный результат, а не повреждает установку.
- [ ] После завершения установки проверяется фактически установленная версия целевого Backend. Только подтверждённое обновление запускает автоматический полный перезапуск Pi и piu по правилам тикета 02, без необходимости вручную вводить `/restart`.
- [ ] После перезапуска видна та же сохранённая сессия и Modal с changelog действительно установленного обновления по правилам тикета 03. Активная работа старого Backend не воспроизводится автоматически.
- [ ] Перезапускается только инстанс, выполнивший `/update`. Другие инстансы продолжают работу, даже если используют тот же установленный Backend; новый бинарник будет использован ими при их собственном следующем запуске.
- [ ] Сетевая ошибка, отказ установщика, недостаток прав или невозможность определить происхождение установки показываются как ошибка без ложного успеха и автоматического перезапуска. Установщик не подменяется случайной командой, привилегии автоматически не повышаются; повторная попытка после устранения причины возможна.
- [ ] Если новая версия не требуется, пользователь получает сообщение об актуальной версии без ненужной переустановки и changelog о несуществовавшем обновлении. Настройки, credentials, сохранённые сессии и personal Extensions не удаляются.
- [ ] Проверки покрывают матрицу из двух Backend и четырёх способов установки, ошибки и повторный вызов. Процессный сценарий подтверждает автоматическую замену обоих процессов, продолжение сессии и changelog после запуска, а сценарий с двумя инстансами — сохранение работы соседнего. Установщики и установки тестовые; реальные менеджеры пакетов и личные программы пользователя не обновляются.

## Comments

- Пользователь подтвердил автоматический перезапуск Pi и piu после успешного `/update` и поддержку curl, npm, pnpm и bun. Под `npn` в сообщении принят npm.
- У stock Pi команда обновления самого Pi отличается от обновления Pi extensions и каталогов моделей. У Pi-Bolt свой updater; документация отдельно описывает установки через менеджеры пакетов, проверку подписей и восстановление набора скомпилированных Pi extensions. Нельзя свести поддержку всех способов к одному глобальному npm install или к запуску случайного бинарника с тем же именем.
- Обновление общего файла установки не означает разрешение закрыть все использующие его процессы. Перезапуск и cleanup ограничены инстансом-инициатором, как в тикете 02.
- Будущая задача: отдельно продумать механизм обновления самого piu — источник и формат релизов, определение способа установки, проверку целостности, безопасную замену, восстановление после сбоя и поведение нескольких инстансов. Этот тикет не устанавливает новые версии piu и не решает заодно его release packaging.
- From 02: автоматический перезапуск после обновления — это `actions.restart()` из `UiActions` (`src/app.tsx`, `leave`). Он завершает Backend, освобождает терминал и через лаунчер `bin/piu.ts` запускает новое приложение с `--session <текущий файл>`. Отдельный перезапуск писать не нужно. Флаги выбора сессии в `backend.args` личного Config при перезапуске не вырезаются. Тест на процессах: `spawnPiu` и `prepareFixture` (`test/process.ts`, `test/harness.ts`), пример в `test/lifecycle.test.ts`.
- From 03: Определение установки (`detectInstall`, id = семейство + realpath команды), источники релизов (`releaseSource`), хранилище версий (`createVersionStore`, файл `$PIU_HOME/backend-versions.json`) и Modal (`changelogModal`) уже есть. Способ установки (curl/npm/pnpm/bun) 03 не определяет — это для `/update`. После обновления Modal откроется сам при следующем запуске, пока предыдущая версия в файле старее установленной; если `/update` перезапускает piu, ничего дополнительно записывать не нужно. Уведомление о доступной версии уже говорит «Run /update».
