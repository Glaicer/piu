# Pi OpenTUI

A terminal UI for the Pi coding agent, built on OpenTUI + Solid. Work is planned in `.scratch/pi-opentui/` (spec and numbered tickets). Use the vocabulary in `GLOSSARY.md`. A bare "extension" means this project's Extension, so say "Pi extension" for Pi's.

Before writing, changing or running tests (including `pnpm check`), read `docs/agents/testing.md`.
Before touching components, focus, keys, scrolling or animations, read `docs/agents/opentui.md`.

## Rules that are easy to get wrong

- **Never write OpenTUI or Pi API calls from memory.** OpenTUI 0.8.x is young and changes fast, and Pi's RPC protocol is specific to each version. Check OpenTUI in Context7 (`/websites/opentui`) and Pi in the docs shipped in `node_modules/@earendil-works/pi-coding-agent/docs/` (`rpc.md`, `rpc-commands.md`, `rpc-extension-ui.md`, `json.md`, `keybindings.md`) against the installed version before using any API. Exact signatures for the installed version live in `node_modules`: Pi's protocol in `@earendil-works/pi-coding-agent/dist/modes/rpc/rpc-types.d.ts` and `dist/modes/json-event.d.ts`, Solid element props in `@opentui/solid/src/types/elements.d.ts`, renderable options in `@opentui/core/renderables/*.d.ts`, and the test renderer in `@opentui/core/testing/*.d.ts`. Runtime behaviour the `.d.ts` hides (setter validation, hit-testing) is in `@opentui/core/index.bun.js` and `chunk-bun-*.js`; grep there. Pi behaviour its docs omit (retries, refusing to compact, turns that end in an error) is in `@earendil-works/pi-coding-agent/dist/core/agent-session.js`, what new, switch and fork do is in `dist/core/agent-session-runtime.js`, when a session file is written is in `dist/core/session-manager.js` (format: `docs/session-format.md`), `@earendil-works/pi-ai/dist/utils/retry.js` and `pi-agent-core/dist/agent-loop.js`; `dist/bundle/` is minified, so never grep it. Read OpenTUI internals from the repo root (`grep -n … node_modules/@opentui/core/index.bun.js node_modules/@opentui/core/chunk-bun-*.js`), and never `cd` into `node_modules`: the pnpm symlink moves the session's working directory into `.pnpm/…`. What the native layer does on its own (terminal queries, modes) is not in the JS: run `strings -a` on `node_modules/.pnpm/@opentui+core-linux-x64*/node_modules/@opentui/core-linux-x64/libopentui.so` and grep it.
- **Runtime is Bun.** OpenTUI needs Bun ≥ 1.3.14 or Node ≥ 26.4, and Node 24 can't run it. `pnpm check` runs tsc, Biome and `bun test`. Fix lint with `biome check --write .`, because `biome format` does not sort imports.
- **`// why:` comments about OpenTUI or Pi quirks are not limited to 1–2 per change.** The limit in the global instructions covers the rest.
- **Pi is a subprocess over RPC, never in-process.** Don't call `createAgentSession` from the app (ADR-0001). Talk to it through the app's own Backend client, not Pi's `RpcClient`, which can only run `node <cli.js>` and copies the child's stderr to our terminal. Frame stdout as LF-only JSONL, never with `readline`, which splits on `U+2028/2029` inside JSON. Never write the Backend's stderr to the terminal. `@earendil-works/pi-coding-agent` is a dev dependency: import only its protocol types, plus the test binary.
- **Tests never touch the developer's Pi.** In the author's shell, `pi` is a function that runs Pi-Bolt under a sandbox. Tests run the pinned dev-dependency `pi` binary directly, with `PI_CODING_AGENT_DIR` set to a temp dir, `PI_OFFLINE=1` and `--no-session`, and the faux model from `@earendil-works/pi-ai`. `startPiu` also passes `--no-skills`, because Pi finds skills under the home folder regardless of `PI_CODING_AGENT_DIR`. A test that needs a saved session (Restart, `-c`) sets `persistSession` instead of `--no-session`; the temp agent dir still keeps it away from the real one.
- **Config merge:** objects merge by key, while arrays and `layout` replace. A replaced `layout` drops the default Placement entries for Panels the new tree lacks, but a `placement` key you write for a missing Panel is a startup error. Unknown keys are startup errors at every level, and the key lists are written out in `src/config.ts` (`topLevelKeys`, `slotKeys`), so a new config section or Slot field goes into them too.
- **A duplicate tool name is a hard startup failure on Pi-Bolt** (ADR-0001). An Extension's Pi extension never reuses another tool's name. To replace a tool, register your own name and drop the old one from `event.systemPromptOptions.selectedTools` in `before_agent_start`. `pi.setActiveTools()` does not hold, because the installed rpiv package re-adds its tool in a `before_agent_start` that runs after ours. A test stand-in for an installed Pi extension must copy behaviour like that (`test/fixtures/pi-extensions/`, placed with `installedPiExtensions`), or it passes on code that fails on the real one. Before writing a stand-in for an installed Pi extension, read the real one's hooks (`pi.on(...)`): the author's installed packages are in `~/.pi/agent/npm/node_modules/` (read-only). Check with `bun scripts/pi-bolt-compat/run.ts`, a manual script that needs your real agent dir: an empty one has no compiled-in Pi extensions. Run it as soon as the Pi extension first works, not at the end of the ticket. In the sandbox it fails with `EACCES` on `~/.pi/agent/trust.json.lock`, so ask the user to run `! bun scripts/pi-bolt-compat/run.ts` and say in the ticket that it is unverified until they do.
- **An Extension's `commands` load only when one of its Modules is in the Placement.** `resolvePlacement` imports an Extension through its placed Modules, so a command-only Extension never reaches `/`. The session commands sit in `builtin/chat` for that reason.
- **Pinned background processes come from the installed `@pify/shell-background`'s sidecar files, not from Pi's RPC** (`builtin/background/`; its widget is a factory, which RPC drops). The sidecar folder name and file format are copied from version 0.7.0, so re-read `~/.pi/agent/npm/node_modules/@pify/shell-background/` when it is upgraded. The pin is enabled only by `background.processes` in the Placement; a Layout without the default `pinned` Panel gets no pin, and its bash cards say `background` instead of the job's status.
- **Subagent cards and the viewer Modal come from the installed `@chthub/pi-subagents`' own leftovers, not from its widget or `/agents`** (those are Pi TUI only; `Pi-Bolt`'s `subagent_subscribe` is not assumed). `builtin/chat/pi-extension.ts` reads the latest `pi-subagents-roster` custom entry of the parent session and each child's session file (its `sessionPath`), and pushes snapshots through reserved `setStatus` keys (`src/subagents.ts`). Both formats are copied from version 0.5.0, so re-read `~/.pi/agent/npm/node_modules/@chthub/pi-subagents/` (`roster-state.ts`, `roster.ts`) when it is upgraded. Pi writes a child's session file only when its first assistant message ends and then one whole message at a time, so the viewer shows nothing until then and no half-streamed text. That Pi extension, like the session commands, loads only while `chat.messages` is in the Placement.
- **The default Backend in `config.ts` stays `pi`.** Personal settings such as `pi-bolt` go in `~/.piu/config.json`, outside the repo, with personal Extensions in `~/.piu/extensions/`; `PIU_HOME` replaces `~/.piu`. The repo has no `config.json` or `extensions/`, so never add one.

## Agent skills

### Issue tracker

Issues and specs live as local markdown files under `.scratch/<feature>/`. Before committing a finished ticket, close it: tick its checkboxes, set `Status: done`, and record every deviation from the ticket under `## Comments`. A leftover that a later ticket owns also goes into that ticket as a `From NN:` comment, or its agent never sees it. See `docs/agents/issue-tracker.md`.

### Triage labels

Default five-role vocabulary, recorded as a `Status:` line in each issue file. See `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `GLOSSARY.md` and `docs/adr/` at the repo root. See `docs/agents/domain.md`.
